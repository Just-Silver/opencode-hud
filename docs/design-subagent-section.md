## 1. 数据来源

结构数据来自宿主 `Context.data` 的 `SessionInfo` 聚合列；首字 / 速度仅在展开时按需补一次子会话消息（见下表）：

| 展示项 | 取法 | 备注 |
| --- | --- | --- |
| 子会话列表 | `context.data.session.family(sessionID)` 去掉自身 | 宿主进入会话时已 `sync(sid, {children: true})` 填充（`CHILD_PAGE = 200` 分页拉全）；子会话结束后**不会**从 family 表移除 |
| 子会话标题 | `session.get(id)?.title` | 主行首列展示；缺失时回退 agent 类型 |
| agent 类型 | `session.get(id)?.agent` | 展开行展示 |
| 耗时 | 见 §2 | |
| 总消耗 | `tokens.input + output + reasoning + cache.read + cache.write` | 会话级累计聚合（`session_v2` 的 `tokens_*` 列），**含缓存读，不排除** |
| 模型 | `session.get(id)?.model?.id` | `ModelRef` 的 `id` |
| 思考强度 | `session.get(id)?.model?.variant` | 可选；缺失则整段不渲染 |
| 缓存命中率 | `tokens.cache.read / (input + cache.write + cache.read)` | 与会话区块同一口径（`model/usage.ts` 的 `cacheRateOf`）；无数据则整行不渲染 |
| 首字 / 速度 | 展开时 `message.sync(id)` → `message.list(id)` → `latestPerf` | **仅展开时取数**；首字与速度分别回溯最近有效样本，与底部同口径 |
| 运行态 | `session.status(id)`：`"运行中"` / `"idle"` | 行首 spinner、耗时口径分支、排序 |
| 结局 | `SessionInfo.outcome`：`succeeded` / `失败` / `interrupted` | 宿主在 execution 终态写 `idle_outcome`（`packages/core/src/session/projector.ts` 的 `projectIdle`）；**只在 `运行中=false` 时采信**（运行中它仍是上一轮的旧值） |
| 结束时刻 | `time.idle ?? time.updated ?? time.created` | **只用于排序**，不展示；运行中不取（见 §2.1） |

不使用 `session.cost`（金额不展示）、不展示 Session ID。**禁止用 `运行中=false` 推断成功**：中断/失败/取消都是 idle。

## 2. 耗时口径

```
运行中：now − time.created
否则   ：(time.idle ?? time.updated) − time.created
```

- `time.idle` 在 `session.execution.succeeded/失败/interrupted` 时写入，语义是「最后一次跑完变空闲的时刻」。
- **运行中时 `idle` 仍是上一轮的旧值、不会清空**，因此必须按 `status()` 分支，不能无条件取 `idle`。
- 不用 `time.updated` 作为结束时刻：它会被 `viewed` / 改名 / 归档等副作用推后（实测主会话 `updated` 比 `idle` 晚 3 分钟）。
- 已知偏差：若子会话被中断后又恢复，`idle − created` 会包含中间空闲期。子代理极少恢复，接受。
- 运行中的条目需要刷新：**仅当存在 运行中 子会话时**开 1s ticker，全部 idle 立即停。

### 2.1 排序与常驻裁剪

```
排序：运行中 在前（组内耗时倒序）→ 已完成按结束时刻倒序 → id 兜底
常驻：全部 运行中 + 最近 VISIBLE_DONE_ROWS（= 5）条已完成；其余折叠成一行
```

- **已完成按结束时刻排序，不按耗时**：耗时倒序会把 `58m` 的老任务压在刚跑完的 `2m` 之上，与「最近 5 条」的筛选口径自相矛盾。
- **运行中条目不设上限**：`family()` 里的子会话结束后不会移除，列表只增不减；任意一条重新进入 `运行中`（复用老子代理）时凭状态自动回到常驻区，再次结束后 `idle` 被刷新，于是成为「最近完成」的头部。
- `VISIBLE_DONE_ROWS = 5`：一次并发通常 3~5 条，再大就会把上方的上下文/额度卡片挤出视野。
- 条数守恒：`head + tail` 的顺序拼接等于原序列，折叠段只是截断，不重排。
- **耗时列不解释排序位置**：排序键是结束时刻，两者不成比例；看到短任务排在长任务之上是正确行为，不要改回耗时倒序。

## 3. 布局

侧栏可用 37 列；圆角卡片边框 2 + 内边距 2 → 内容 **33 列**。几何常量在 `view/layout.ts`（`AGENT_*`），不实测。

视觉分层（Native Pro）：

- **运行中**：两行任务卡——抬升底色 `RAISED_COLOR` + 左侧琥珀强调线 + spinner + 加粗标题；第二行 `耗时 · 消耗 tok`。点击任意一行展开详情。
- **已停止**：单行紧凑行，结局点按 `outcome` 上色（成功绿 / 失败红 / 中断琥珀 / 未知灰），标题次级色。

### 3.1 卡片头与表尾

```
● 1 运行中  3 已停止            ← 运行中（绿）/ 已停止（次级）/ N 失败（红）
...
收起                 合计 390.8M  ← 表尾：收起全部（有展开项时）+ 合计消耗
```

- 三个计数各自独立：失败不藏进「已停止」；数字为 0 的计数不渲染。
- `合计` 是各子代理真实累计消耗之和（含缓存读），始终显示；`收起` 只在有展开项时可点。

### 3.2 已停止行（1 行）

```
▶ ● Final cleanup f…      1h57m   19.6M
```

列预算（内容 33）：

```
箭头 2 + 结局点 2 + 标题(≤15) + 垫片 + 耗时 6 + 空格 1 + 总消耗 6
```

- 标题列超宽用 `truncateVisual`；两个数值列 `padStartVisual` 定宽，右缘严格对齐。
- 展开时在下方补 `Details`（缩进 2，不加底色）。

### 3.3 运行中任务卡（2 行 + 详情）

```
▍⠋ Refactor API                    ▸
▍ 2m18s · 1.2M tok
```

- 左侧线由 `border={["left"]}` + 琥珀 `borderColor` 实现，右侧箭头表示展开态。
- 内宽 30：spinner 2 + 标题(≤26) + 垫片 + 箭头 1。
- 第二行是 `fmtElapsed · fmtTokens tok`（`tok` 明确单位，避免裸数字歧义）。
- 点击卡片任意一行切换展开。

### 3.4 展开详情（最多 +6 行）

```
  标题 最终审查三库拆分（完整，不截断，超宽自动换行）
  状态 完成
  模型 deepseek-v4.1-flash (high)
  代理 general
  命中 98.4%
  性能 0.42s · 48 tok/s
```

- 值列上限 23 列（运行中块内宽 30 − 7 缩进 = 23，已停止行共用这个上限以免溢出）。
- 状态行颜色与结局点一致；失败/中断在颜色之外还有文字。
- 空值行整行不渲染。

### 3.5 历史折叠

- 常驻最近 5 条已完成，其余进 `▶ 还有 N 条已完成`；展开态是独立内存态，与逐条展开互不影响。
- 点「收起」两个一起收（只收一半读起来像没收干净）。

## 4. 边界与不做的部分

- 无子代理 → 整块不渲染
- 只做**单层折叠**，不做分页 / 虚拟滚动 / 回顶：侧栏本就由宿主 `scrollbox` 包裹
- 不做「进入会话」跳转：宿主 footer 自带的 `N subagents` 已可跳转
- 不做持久化 / TTL / 多实例合并 / 僵尸清理：实时从 `family()` 读
- 不做 `task` 工具 part 反查：`family()` 是宿主官方 API
- 入口来源区分（工具调用 vs `spawn`）不展示
- 不做任务进度百分比：宿主不提供，不编造
- 不做整卡折叠：卡片折叠后只剩空边框

## 5. 已知取舍

- 常驻裁剪只省视觉高度，不省数据量：19 条时仍要读 19 个 `session.get(id)`（本地内存查询）。
- 折叠行展开态是组件内存态，切换会话后回到默认折叠；与逐条展开态一样不持久化。
- **首字 / 速度只在展开时取**：首次展开对子会话做一次 `message.sync(id)`（最近 20 条消息），之后宿主 `step.ended` 写回同一 Solid store，展开行自动更新；不轮询、不新增定时器。
- 性能显示的是最近有效样本的精确值（首字与速度分别回溯，与底部 `latestPerf` 同口径），不是整段平均。
- 消息窗口只有 20 条；窗口内全是被守卫拦下的步时，不向前翻页、不猜，整行不渲染。
- 极低概率竞态：展开恰好落在子会话 `step.started` 与 `message.sync` 响应之间时，宿主 `reconcile` 可能裁掉刚插入的 assistant 行；不崩，下一步事件会自愈。
- `family()` 依赖宿主已同步子会话列表；宿主进入会话路由时本来就会做 `sync(children)`，正常路径无需我们触发。
