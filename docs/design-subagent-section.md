## 1. 数据来源

结构数据来自宿主 `Context.data` 的 `SessionInfo` 聚合列；首字 / 速度仅在「展开中 或 运行中」时按需补一次子会话消息（见下表）：

| 展示项 | 取法 | 备注 |
| --- | --- | --- |
| 子会话列表 | `context.data.session.family(sessionID)` 去掉自身 | 宿主进入会话时已 `sync(sid, {children: true})` 填充（`CHILD_PAGE = 200` 分页拉全）；子会话结束后**不会**从 family 表移除 |
| 子会话标题 | `session.get(id)?.title` | 主行首列展示；缺失时回退 agent 类型 |
| agent 类型 | `session.get(id)?.agent`；显示名按 `location.agent.list()` 的 id 匹配 `name` | 匹配不到回退 id；运行中主行第 2 行，已停止在展开行 |
| 耗时 | 见 §2 | |
| 总消耗 | `tokens.input + output + reasoning + cache.read + cache.write` | 会话级累计聚合（`session_v2` 的 `tokens_*` 列），**含缓存读，不排除** |
| 模型 | `session.get(id)?.model?.id`；显示名按 `location.model.list()` 的 `providerID + id` 匹配 `name` | 匹配不到回退 id；运行中主行第 3 行 |
| 供应商 | `model.providerID` → `location.provider.list()` 的 `name` | 匹配不到回退 providerID；运行中主行第 2 行 |
| 思考强度 | `session.get(id)?.model?.variant` | 可选；缺失则整段不渲染；运行中主行第 3 行 |
| 缓存命中率 | `tokens.cache.read / (input + cache.write + cache.read)` | 与会话区块同一口径（`model/usage.ts` 的 `cacheRateOf`）；运行中主行第 4 行，已停止在展开行；无数据则整段不渲染 |
| 首字 / 速度 | 展开中或运行中：`message.sync(id)` → `message.list(id)` → `latestPerf` | 已结束且未展开的条目不取数；首字与速度分别回溯最近有效样本，与底部同口径 |
| 运行态 | `session.status(id)`：`"运行中"` / `"idle"` | 行首 spinner、耗时口径分支、排序 |
| 结局 | `SessionInfo.outcome`：`succeeded` / `失败` / `interrupted` | 宿主在 execution 终态写 `idle_outcome`（`packages/core/src/session/projector.ts` 的 `projectIdle`）；**只在 `运行中=false` 时采信**（运行中它仍是上一轮的旧值） |
| 结束时刻 | `time.idle ?? time.updated ?? time.created` | **只用于排序**，不展示；运行中不取（见 §2.1） |

不使用 `session.cost`（金额不展示）、不展示 Session ID。**禁止用 `运行中=false` 推断成功**：中断/失败/取消都是 idle。

## 2. 耗时口径

```
运行中：now − time.created
否则   ：(time.idle ?? time.updated) − time.created
```

- `time.idle` 在 `session.execution.succeeded/失败/interrupted` 时写入，语义是「最后一次跑完变空闲的时刻」。
- **运行中时 `idle` 仍是上一轮的旧值、不会清空**，因此必须按 `status()` 分支，不能无条件取 `idle`。
- 不用 `time.updated` 作为结束时刻：它会被 `viewed` / 改名 / 归档等副作用推后（实测主会话 `updated` 比 `idle` 晚 3 分钟）。
- 已知偏差：若子会话被中断后又恢复，`idle − created` 会包含中间空闲期。子代理极少恢复，接受。
- 运行中的条目需要刷新：**仅当存在 运行中 子会话时**开 1s ticker，全部 idle 立即停。

### 2.1 排序与常驻裁剪

```
排序：运行中 在前（组内耗时倒序）→ 已完成按结束时刻倒序 → id 兜底
常驻：全部 运行中 + 最近 VISIBLE_DONE_ROWS（= 5）条已完成；其余折叠成一行
```

- **已完成按结束时刻排序，不按耗时**：耗时倒序会把 `58m` 的老任务压在刚跑完的 `2m` 之上，与「最近 5 条」的筛选口径自相矛盾。
- **运行中条目不设上限**：`family()` 里的子会话结束后不会移除，列表只增不减；任意一条重新进入 `运行中`（复用老子代理）时凭状态自动回到常驻区，再次结束后 `idle` 被刷新，于是成为「最近完成」的头部。
- `VISIBLE_DONE_ROWS = 5`：一次并发通常 3~5 条，再大就会把上方的上下文/额度卡片挤出视野。
- 条数守恒：`head + tail` 的顺序拼接等于原序列，折叠段只是截断，不重排。
- **耗时列不解释排序位置**：排序键是结束时刻，两者不成比例；看到短任务排在长任务之上是正确行为，不要改回耗时倒序。

## 3. 布局

侧栏可用 37 列；圆角卡片边框 2 + 内边距 2 → 内容 **33 列**。几何常量在 `view/layout.ts`（`AGENT_*`），不实测。

视觉分层（Native Pro）：

- **运行中**：五行任务卡——抬升底色 `RAISED_COLOR` + 左侧绿色强调线（与 spinner / 计数同色 `stateColor("running")`）+ spinner + 加粗标题；第二行 `agent · 供应商`；第三行 `模型 · 强度`；第四行 `耗时 · 消耗 · 缓存命中`；第五行 `首字 · 速度`（无有效样本时整行不渲染）。点击任意一行展开详情。
- **已停止**：单行紧凑行，状态点按**黄色** `WARNING_COLOR`（成功 / 中断 / 未知结局共用黄），**失败用红**；标题次级色。
- **绿色专指「运行中」**：运行中 spinner 与卡片头计数点都用绿 `SUCCESS_COLOR`；已停止的点**不能用绿**——同一条列表里「正在跑」与「已跑完」同色就失去区分（v3.1.0 的绿=运行中、黄=已停止，2026-11-11 的 HUD 5.0 曾把绿改给「成功」，已改回）。

### 3.1 卡片头与表尾

```
●   0  ● 200  ●   5   合计   1.2M   ← 无展开项
●   0  ● 200  ●   5          收起   ← 有展开项
...
```

- 计数口径：三个**状态胶囊**（底色块 + 灯 + 定宽数字 + 右侧 1 列留白，块间留 1 列卡片底），灯与数字同色：绿=运行中、黄=已停止、红=失败；不写「运行中 / 已停止 / 失败」文字。运行中与已停止常驻显示，0 也显示（全停与全跑必须一眼可分，不给空转噪音也不隐藏），失败为 0 时整块不渲染。
  - **互斥口径（2026-11-16 用户确认）**：`subagentCounts` 的三个数字互斥，`running + stopped + failed = 总行数`；`stopped` 只数非失败的已停止（`stopped = 总行数 − running − failed`），未知/`interrupted`/`stopped` 都进 `stopped`，失败不重复计入。
- **每个胶囊自带状态底色**（`SUCCESS_WASH_COLOR` / `WARNING_WASH_COLOR` / `ERROR_WASH_COLOR`，状态色的暗调）：底色本身就是状态，不靠「灯是什么颜色」去猜；三块颜色不同，也就不会连成一条。
- 终端没有圆角/胶囊原语（OpenTUI 无 `borderRadius`，`rounded` 是矩形边框）；胶囊就是「背景色块 + 留白」，与宿主 `StatusBadge` 同一做法。**胶囊左侧不留白**是宽度取舍：33 列要同时放下三个胶囊与合计，6 列/块（`● 200 `）已是上限，再加左留白就会把合计挤掉。
- **数字定宽右对齐 3 位**（`AGENT_COUNT_NUM_WIDTH = 3`，空格补齐，不补零）、合计定宽 6 位（`AGENT_TOTAL_WIDTH`）：胶囊宽度不随 `0 → 200` 变化，合计从 `1.2M` 涨到 `390.8M` 时「合计」标签也不左移。3 位是实测所需（长会话的已停止数已过 200）。
- `合计` 是各子代理真实累计消耗之和（含缓存读），贴在计数行右端，**只在无展开项时显示**；计数区可收缩（`flexShrink`），窄侧栏下先裁计数也不把合计挤掉。
- `收起` 固定在**卡片头右端**，且**只在有展开项时渲染**（平时不留空行）。放在表尾时，历史段展开几十条后要先滚到底才能收；表头是卡片内唯一不会随列表长度下沉的位置。
- 展开期间 `收起` **顶替** `合计`：33 列里两者同时出现会把计数裁掉；收起后合计立即回来。

### 3.2 已停止行（1 行）

```
▶ ● Final cleanup f…      1h57m   19.6M
```

列预算（内容 33）：

```
箭头 2 + 结局点 2 + 标题(≤15) + 垫片 + 耗时 6 + 空格 1 + 总消耗 6
```

- 标题列超宽用 `truncateVisual`；两个数值列 `padStartVisual` 定宽，右缘严格对齐。
- 展开时在下方补详情（缩进 2，`RAISED_COLOR` 抬升底色），不与主行同底色。

### 3.3 运行中任务卡（5 行 + 详情）

```
▍⠋ Refactor API                    ▸
▍ explore                  Open Design
▍ DeepSeek V4.1 Flash            high
▍ 2m18s · 1.2M             缓存 98.4%
▍ 0.42s                   48 tok/s
```

- 左侧线由 `border={["left"]}` + `borderColor={stateColor("running")}`（绿）实现，与行首 spinner、卡片头计数同色；右侧箭头表示展开态。
- 内宽 30：spinner 2 + 标题(≤26) + 垫片 + 箭头 1。
- 第 2 行 `agent 显示名`（左）· `供应商名`（右）：agent 名按 `location.agent.list()` 的 id 匹配 `name`（如 `qa` → `QA`、`explore` → `Explore`），查不到回退 id；供应商缺失时右列不渲染，左列占满。
- 第 3 行 `模型名`（左）· `强度`（右）：模型与供应商名来自宿主目录（`model/subagent.ts` 的 `subagentLabels`），按 `providerID + id` 双键匹配 `name`，查不到回退 id。
- 第 4 行 `耗时 · 消耗`（左）· `缓存率`（右）：缓存率标签用弱化色、数值用 `CACHE_COLOR`（与展开区一致）；无缓存数据时右列不渲染。最坏组合 `58m05s · 999.9k` + 1 + `缓存 100.0%` 占 27 列，`tests/layout.test.ts` 钉住不换行。
- 第 5 行 `首字`（左）· `速度`（右）：还没有可用样本时整行不渲染，不占位。
- 双列统一由 `TwoCol` 承担：先算右列宽度再截断左列（`truncateVisual`），中间空白由 `flexGrow` 吸收，不手写空格。
- **展开只影响标题**：收起时标题按 `AGENT_RUNNING_TITLE_MAX` 截断；展开后同一行改为全文并按字符换行（`wrapMode="char"`），其余四行完全不变，**不额外渲染详情块**。运行中不维护第二套 UI。

### 3.4 展开详情（Task Inspector，只服务已停止条目）

已停止主行是单行摘要，展开补全与运行中相同顺序的信息行：

```
  最终审查三库拆分（完整标题，按字符换行）
  Reviewer                 Open Design
  Hy4 Flash Free                 high
  2m52s · 558k           缓存 88.5%
  2.94s                   207 tok/s
```

- 行序与运行中的四行完全一致：Agent · 供应商 / 模型 · 强度 / 耗时 · 消耗 · 缓存率 / 首字 · 速度；颜色也一致（agent `MUTED`、供应商与模型 `SECONDARY`、缓存标签 `MUTED` + 数值 `CACHE_COLOR`、首字/速度 `SECONDARY`）。
- 完整标题沿用收起态的 `SECONDARY_COLOR`、不加粗：展开只补信息，不改变同一行文字的强调。
- 双列：左列左对齐、吃剩余宽度（可换行），右列贴右缘；中间靠弹性盒留白，不手写空格。
- **运行中不渲染本组件**：运行中展开只把标题换成全文（§3.3），避免同一屏出现两份相同指标。
- 版心 27 列（运行中卡片内宽 30 − 左右内边距 3，`AGENT_INSPECTOR_INNER`；已停止行共用这个上限以免溢出）。

### 3.5 历史折叠

- 常驻最近 5 条已完成，其余进 `▶ 还有 N 条已完成`；展开态是独立内存态，与逐条展开互不影响。
- 点「收起」两个一起收（只收一半读起来像没收干净）。

## 4. 边界与不做的部分

- 无子代理 → 整块不渲染
- 只做**单层折叠**，不做分页 / 虚拟滚动 / 回顶：侧栏本就由宿主 `scrollbox` 包裹
- 不做「进入会话」跳转：宿主 footer 自带的 `N subagents` 已可跳转
- 不做持久化 / TTL / 多实例合并 / 僵尸清理：实时从 `family()` 读
- 不做 `task` 工具 part 反查：`family()` 是宿主官方 API
- 入口来源区分（工具调用 vs `spawn`）不展示
- 不做任务进度百分比：宿主不提供，不编造
- 不做整卡折叠：卡片折叠后只剩空边框

## 5. 已知取舍

- 常驻裁剪只省视觉高度，不省数据量：19 条时仍要读 19 个 `session.get(id)`（本地内存查询）。
- **性能基准（2026-11-16，纯函数）**：1000 条已完成 + 1 条运行中时，按 `useSubagents` 的形状对全部 id 做一次 `Map.get` + `buildRow` 再 `sortRows`，实测平均 0.08–0.11 ms、p95 上限 0.272 ms（Node 24 / win32）。当前**有意保持全量重算**，不引入 running/done memo 或行引用复用；未测 OpenTUI 布局/渲染与进程 CPU，不能据此声称 TUI 整体流畅——这些数值只排除「纯函数是瓶颈」，不是 TUI CPU 实测。
- 折叠行展开态是组件内存态，切换会话后回到默认折叠；与逐条展开态一样不持久化。
- **首字 / 速度只在展开中或运行中时取**：对这类子会话做一次 `message.sync(id)`（最近 20 条消息），之后宿主 `step.ended` 写回同一 Solid store，行内自动更新；不轮询、不新增定时器。已结束且未展开的条目零请求。
- 性能显示的是最近有效样本的精确值（首字与速度分别回溯，与底部 `latestPerf` 同口径），不是整段平均。
- 消息窗口只有 20 条；窗口内全是被守卫拦下的步时，不向前翻页、不猜，整行不渲染。
- 极低概率竞态：展开恰好落在子会话 `step.started` 与 `message.sync` 响应之间时，宿主 `reconcile` 可能裁掉刚插入的 assistant 行；不崩。已知限制（2026-11-16）：`message.sync` 只取最近 20 条并 `reconcile` 替换该会话缓存；可能替换其他视图已加载的更早历史；插入行与响应交错时可能被裁掉且后续事件不会补回；未实机复现。
- `family()` 依赖宿主已同步子会话列表；宿主进入会话路由时本来就会做 `sync(children)`，正常路径无需我们触发。
