### 2.1 更新与安装：失败不再破坏旧版、不丢结果

- `update/apply.ts` 的 `installAtomically` 改为事务式替换：随机容器内 `stage/` + `backup/`，先把旧目录整体挪到备份，再提升新副本；提升失败回滚旧版，回滚失败保留唯一备份并在错误信息里给出可恢复路径。容器根没有 `tui.tsx`，失败残留不会被宿主发现成第二个插件。

- 证据：显式自定义配置根与显式 `OPENCODE_DB` 已修；但 `ctx.app.channel` 可能只是 `OPENCODE_TUI_CHANNEL` 的显示覆盖，不等于 server 数据库频道；不能扫描/回退任意 `opencode*.db`；远程会话两侧 env 可能不同（`quota-audit` Q2/Q3/Q4/Q9 剩余）。
- 场景：源码运行/非默认频道使用 `opencode-<channel>.db`，或 TUI 连接远程 server；当前仍读进程 cwd 对应的本地配置与默认 DB。
- 选择：A. 统一解析器并获取宿主有效连接/服务端能力；B. 继续只支持本机默认连接，把限制写清。
- 建议：A 是正确方向，但需要宿主公开能力；不要把 `ctx.app.channel` 直接当 server 频道，也不要扫描其他账号库。

### 4.4 OAuth 稳定身份（中）

- 证据：缓存按 token 哈希分桶；同一账号 token 刷新也会换桶、清数据并触发计划外请求（Q5）。refresh token 也可能轮换，不能当稳定 ID。
- 场景：OAuth access token 自动刷新后，额度短暂消失并多发一次请求。
- 选择：A. 引入 credential id 等稳定身份，改解析器/store 契约；B. 接受刷新时的短暂清空。
- 建议：A；在契约明确前不要用 refresh token 充当稳定 ID。

### 4.5 企业 Console（中）

- 证据：当前忽略 `metadata.server`；企业额度端点未验证（Q8）。
- 场景：企业 Console 登录的凭据被发往公共额度主机，或该账号额度查不到。
- 选择：A. 增加可信主机策略与企业端点验证；B. 暂不识别企业账号，按无数据隐藏。
- 建议：先拿到真实脱敏响应与主机白名单，再接入；不要凭猜测把凭据发向新主机。

### 4.6 三个子代理计数是否互斥（中）

- 证据：`subagentCounts` 的 `stopped = rows.length - running`，**包含 failed**；`tests/perf.test.ts` 固化了 inclusive 语义，源码注释已改为同一口径（三项不互斥）。
- 场景：1 running + 1 failed + 1 succeeded 显示 `1 / 2 / 1`，三数相加多于实际行数。
- 选择：A. 维持“非运行中（黄，含失败）+ 其中失败（红）”，修文案；B. 改为互斥三桶 `stopped = 非运行中 − failed`。
- 建议：由用户定口径后同步注释、AGENTS、设计文档与测试；本次只在文档标注，不改计数。
- 后续：2026-11-16 已按 §8 项 6 改为互斥三桶（见 `model/subagent.ts` 与 `tests/perf.test.ts`）。

### 4.7 发版回推 main 与门禁（中高，流程风险）

- 证据：`release.yml` 直接 `git push origin HEAD:main`，无祖先校验/排队；非 main tag 可能把提交推入 main；main 前进会让 job 在创建 Release 前失败；工作流不跑测试（F4/F15）。
- 场景：从特性分支打 tag，或发版期间 main 有新提交。
- 选择：A. 限定 tag 来源、加 `merge-base --is-ancestor`、`concurrency` 排队与失败告警；B. 维持手工流程。
- 建议：A；并把 Release 创建与 push 解耦（push 失败仍能出 Release 或明确告警），新增 CI 跑测试/esbuild。

### 4.8 正式版 / 预发布策略（中）

- 证据：workflow 仅 `v*`，版本校验只抽 `x.y.z`，`prerelease: false`；`parseVersion` 拒绝 `-rc`；`git ls-remote` 回退可能选中更高的 rc tag；更新器按 `v` 前缀重建 URL（F5/F6）。
- 场景：有人打 `v6.0.0-rc.1`，或 curl 302 失败走 git 回退。
- 选择：A. 明确只发正式 `vX.Y.Z`，三处一致地拒绝预发布；B. 完整支持 SemVer 预发布并保留原始 tag。
- 建议：A 更简单；当前没有 `v` 前缀的 tag 不在公开发版约定内，不把它算成当前稳定流程的必现 bug。

### 4.9 更新下载与供应链加固（中）

- 证据：归档 `arrayBuffer()` 无大小上限、无校验和；Actions 使用浮动大版本 tag（F7/F14）。
- 场景：代理/上游返回异常大响应；或需要可验证的发布产物。
- 选择：A. 增加归档大小上限/流式写盘/发布 checksum/固定 Action SHA；B. 维持 TLS 信任。
- 建议：A 作为加固政策；不要直接套用额度 JSON 的 8MB/5s 限制（归档体积与超时需求不同），也不声称 HTTPS 本身已不安全。

### 4.10 旧名称迁移清理的兼容窗口（中）

- 证据：TODO 原定 v4.6.0 后移除，当前已是 5.x；`install.*`、`uninstall.*`、`update/apply.ts` 的旧目录清理仍在，AGENTS 仍要求保留（D13）。
- 场景：仍停在 v4.1.x 的用户升级；或现在删除保护后旧目录残留导致双实例。
- 选择：A. 立即结束兼容窗口并删清理点；B. 保留，另定新的复查版本。
- 建议：B，直到用户确认旧用户覆盖情况；不要因版本号已过就删保护。本次已在 TODO/AGENTS 标明冲突与待决入口。

### 4.11 并发锁、断电恢复与临时副本/备份的保守清理（中）

- 已修：安装脚本提升前写入本次安装的身份标记、提升后读回校验，回滚同样校验「旧版是否真的落回目标」；「检查 → 移动」在提升与回滚两个窗口里的误报已由真实脚本回归覆盖（见 §2.1）。Node 更新器用 `rename` 语义，不受同一嵌套问题影响。
- 仍未处理：序列本身没有跨进程锁（两个安装都在身份校验前也可能互相挪动旧版）；断电或 `kill -9` 可能留下随机事务容器（其中 `backup/` 可能是唯一旧版）；旧版遗留的固定 stage `plugins/.tmp.opencode-hud` 不会被新安装清理，若含 `tui.tsx` 会被宿主当成第二个插件（卸载脚本会清理）。
- 手工清理边界：先确认正式安装可用（`<全局配置根>/plugins/opencode-hud/tui.tsx` 存在、宿主能加载该插件），再确认残留里的备份已无恢复价值，最后手工删随机容器；**回滚失败或身份校验失败后不要递归删除容器**——那里面可能是唯一旧版，应按脚本打印的路径先核对内容，再决定保留还是移回。
- 场景：并发安装/更新、断电、旧版失败残留。
- 选择：A. 增加锁与恢复指引、按年龄保守清理旧固定 stage；B. 只保留当前回滚与身份校验，不做并发/恢复。
- 建议：先讨论锁与自动清理的归属再动手；备份清理必须保守，不能删唯一副本。

### 4.12 大规模子代理与共享消息同步（中低）

- 证据：有子代理在跑时，`useSubagents` 每秒对全部历史行 `session.get` + `buildRow` + 排序；机制确定，但没有规模基准。`message.sync` 可能 reconcile 另一 tab 已加载的历史；probe 重挂可能错过结果（view F5/U2/U3）。
- 场景：长会话沉淀数百条已停止子代理；多 tab/重挂。
- 选择：A. 拆分 running/done memo 或做引用复用；B. 维持并在注释声明有意全量重算。
- 建议：先做规模基准与定向 TUI 复现，再决定是否重构；不要用未实测的 CPU 数字推动大改。

### 4.13 终端宽度与歧义字符（低）

- 证据：`visualWidth` 的 Ambiguous 符号与部分 emoji 表不全；当前未证实可观察错位（view U1、quota D9）。
- 场景：特定终端/字体把 `↻`、箭头或 emoji 渲染成不同列宽。
- 选择：A. 收集用户终端/字体样本，补充宽度表与用例；B. 维持现状。
- 建议：用真实终端核验，不能用同一个 `visualWidth` 函数自测自证。

### 4.14 用宿主原生 `usage.limits` 替代手工凭据查询（架构级）

- 证据：本机宿主 API 已有 `ctx.client.experimental.usage.limits({ location })`（旧别名 `ctx.client.usage.limits()` 已标 deprecated，会在下个小版本移除）；当前 `opencode-go` 仍走手工凭据 + HTTP。
- 场景：减少凭据读取与端点维护，统一额度来源。
- 选择：A. 迁移到宿主 API；B. 保留现有 provider 契约。
- 建议：先验收刷新语义、错误口径、展示字段与宿主版本兼容，再单独设计；不要顺手切换。

### 4.15 旧配置安装文档升级、忽略模板精简、日志展示增强（低，可选）

- 证据：`docs/config-install.md` 已标 2.0.x 历史快照并修可确认路径，但整篇未升级到 2.2.6；根 `.gitignore` 404 行包含与本仓库无关的模板项；`cliff.toml` 的 compare 链接与跳过 chore 条目属可选增强。
- 场景：新插件复用旧方法学；维护者阅读噪音。
- 选择：A. 整篇升级/精简/增加发布链接与过滤；B. 保留历史与现有输出。
- 建议：B 为默认；只有该文档被实际复用或发布输出需要 compare 链接时再做，不无故删历史或改发布格式。

### 4.16 环境变量 trim / 空串语义与宿主的差异（低）

- 证据（按变量分项）：
  - `OPENCODE_CONFIG_DIR`：宿主 `packages/util/src/global.ts` 用 `??`（空串被当成有效值 `""`）；插件 `globalConfigDir()` 先 trim，空串视为未设置。
  - `OPENCODE_DB`：宿主 `packages/cli/src/database-path.ts` 用 `??`（`""` 会解析成 dataDir）；插件 `quota/key.ts` 的 `databaseFile()`（157-161 行）只把 `undefined`/空串当未设置、仍读 `opencode.db`，**不 trim**——带首尾空白时插件与宿主都把它当原样文件名。
  - `XDG_CONFIG_HOME` / `XDG_DATA_HOME`：宿主 `packages/util/src/global-roots.ts` 用 `||`（空串回退到默认目录）；插件也是空串视为未设置，但对带首尾空白的值同样一律 trim。
  - 安装脚本：只有 PowerShell 是 `Trim()` 判空后返回原值；Bash 的 `${VAR:-默认}` 只把未定义/空串当未设置，**不 trim**。
- 场景：人为把上述变量设成空串或带首尾空白（含 Windows 路径末尾空格）。
- 选择：A. 保留插件现状（配置根与 data 目录先 trim；`OPENCODE_DB` 只判空串、不 trim）并记录差异；B. 完全对齐宿主的原样拼接 / `||` 回退语义。
- 建议：A 只是记录现状，不改行为；不把 trim 一概说成「更安全/更健壮」——带首尾空白的合法路径该按原样还是按 trim 后处理仍是待决问题（涉及空格结尾目录、脚本与插件一致性），本波不动实现。

## 5. 不作为当前缺陷处理
